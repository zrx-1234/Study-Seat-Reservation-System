# 自习座位预约系统小组分工安排文档

## 1. 引言

### 1.1 小组成员
小组共有6名成员，按照功能模块分为三个部分，每部分2人：
- **系统-管理员部分**：成员A、成员B
- **系统-学生部分**：成员C、成员D
- **AI智能化部分**：成员E、成员F

### 1.2 分工原则
- **模块单一负责人**：每个v2架构模块有且仅有一个负责小组
- **分层协作**：基于v2架构的接口层、领域层、基础设施层进行分工
- **代码文件不重叠**：各小组负责的代码文件明确边界，避免并行开发冲突
- **共享公共基础**：基础设施层由管理员组统一维护，其他组仅调用不修改

---

## 2. 基于v2架构的模块分工

### 2.1 架构模块总览
系统采用v2架构设计，分为：
- **接口层（API Layer）**：3个模块
- **领域层（Domain Layer）**：6个模块
- **基础设施层（Infrastructure Layer）**：5个模块

### 2.2 模块-小组映射表

| 层级 | 模块标识 | 模块名称 | 负责小组 | 说明 |
|------|---------|---------|---------|------|
| **接口层** | `API-ADM` | 管理端接口模块 | 管理员组 | `backend/api/admin.py` |
| | `API-STU` | 学生端接口模块 | 学生组 | `backend/api/student.py` |
| | `API-AI` | AI助手接口模块 | AI组 | `backend/api/ai.py` |
| **领域层** | `MOD-USER` | 用户与权限模块 | 管理员组 | `backend/domain/user/*` |

| | `MOD-SYS` | 系统配置模块 | 管理员组 | `backend/domain/system/*` |
| | `MOD-AI` | 智能助手模块 | AI组 | `backend/domain/ai/*` |

## 4. 代码协作规则

### 4.1 文件修改权限
| 小组 | 可修改的文件 | 只读不可修改的文件 |
|------|------------|-----------------|
| 管理员组 | 自己负责的所有文件 | 无（可修改全部，但不建议修改学生组和AI组的文件） |
| 学生组 | 自己负责的文件 | 管理员组和AI组的所有文件 |
| AI组 | 自己负责的文件 | 管理员组和学生组的所有文件 |

### 4.2 分支策略
- `main`：稳定分支，仅合并已通过自测的功能
- `feature/admin-xxx`：管理员组功能分支
- `feature/student-xxx`：学生组功能分支
- `feature/ai-xxx`：AI组功能分支

### 4.3 代码审查
- 修改自己负责的文件：自行审查或小组内审查
- 修改公共文件（仅管理员组可修改）：需另一组成员审查
- 跨组调用接口：确保接口契约稳定，变更需提前通知

### 5.2 API接口共享
- **后端服务**：所有部分共享统一的Domain Service接口
- **数据层**：共享数据库（MySQL），通过ORM访问，不直接跨模块操作表
- **交互方式**：
  - 学生组通过 `domain.room.service` 查询座位
  - AI组通过 `domain.room.service` 和 `domain.reservation.service` 查询数据
  - 所有组通过 `infrastructure.*` 使用基础设施能力

### 5.3 协作机制
- **代码仓库**：使用GitHub代码库，分支管理
- **接口文档**：维护v2架构设计文档中的接口契约
- **会议**：每周站会，讨论进度、接口变更、集成问题
- **测试**：各小组负责自己模块的单元测试和接口测试

## 6. 完成整个项目的工作流

### 6.1 总体工作流（基于Scrum和GitHub）
1. **需求分析阶段**（第1周）：
   - 识别用户故事（所有成员参与）。
   - 定义需求规格，分配到各部分。

2. **设计阶段**（第2-3周）：
   - v2架构设计（共享文档）。
   - API契约设计、数据库设计。
   - 各部分UI/UX设计。

3. **开发阶段**（第4-10周）：
   - 并行开发：各小组独立开发自己负责的模块。
   - 每日提交代码，自动化测试。
   - 每周集成：合并分支，解决冲突。

4. **测试阶段**（第11-12周）：
   - 单元测试、集成测试、端到端测试。
   - 用户验收测试（UAT）。

5. **部署阶段**（第13-14周）：
   - GitHub Actions流水线：构建、测试、部署。
   - 生产环境上线。

6. **维护阶段**（第15-16周）：
   - Bug修复、性能优化。
   - 项目汇报准备。

### 6.2 具体工作流步骤
- **迭代周期**：2周一个Sprint。
- **任务分配**：在GitHub Projects中创建用户故事，按模块分配给各小组。
- **进度跟踪**：使用思维导图和Scrum板。
- **质量保证**：代码审查、自动化测试覆盖率>80%。
- **交付物**：代码、测试报告、文档、演示视频。

### 6.3 时间安排（基于lab阶段）
- **第一阶段（第5周Review）**：完成初步架构和1-2个用户故事。
- **第二阶段（第12周Review）**：实现>50%功能，完整DevOps流程。
- **项目汇报（15-16周）**：完整功能展示。

## 7. 风险管理

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 模块接口变更影响其他组 | 高 | 接口变更需提前通知，保持向后兼容 |
| 进度不一致，集成困难 | 中 | 每周强制合并到main一次，早发现早解决冲突 |
| 公共模块修改引发Bug | 中 | 公共模块仅管理员组可修改，修改需充分测试 |
| 数据库查询性能差 | 中 | 预留数据库索引优化和查询优化时间 |

## 8. 结论

此分工安排基于v2架构设计，确保：
- ✅ 每个模块有单一负责人
- ✅ 各小组代码文件边界清晰，不重叠
- ✅ 通过Service接口实现跨组协作，避免直接依赖
- ✅ 基础设施层统一管理，保证技术一致性
- ✅ 遵循DevOps实践，保证项目高质量完成
