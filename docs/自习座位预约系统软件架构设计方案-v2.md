# 自习座位预约系统 — 软件架构设计方案（v2）

> 版本：v2.0
> 日期：2026-05-13
> 适用范围：系统全部后端模块、前端模块及外部集成
> 设计目标：以业务领域（Domain）为核心进行模块划分，明确模块边界与模块间接口契约，降低耦合、提升内聚，支撑多团队并行开发与长期演进。

---

## 1. 引言

### 1.1 编写目的

本文档从软件工程视角出发，对自习座位预约系统进行科学的模块划分与架构设计，明确：
- 系统包含哪些**业务领域模块**；
- 每个模块的**职责范围**与**对外暴露的接口**；
- 模块间的**依赖关系**与**调用约定**；
- 系统的**分层架构**与**数据流**。

本文档作为编码实现的顶层约束，各模块实现必须遵循本文档定义的接口契约。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **领域优先（Domain-Driven）** | 按业务领域（用户、自习室、预约、通知等）划分模块，而非按前端用户角色（学生/管理员）划分 |
| **分层架构（Layered Architecture）** | 严格区分接口层（API Layer）、领域层（Domain Layer）、基础设施层（Infrastructure Layer） |
| **依赖倒置（Dependency Inversion）** | 上层模块依赖下层模块的抽象接口，禁止跨层反向依赖与循环依赖 |
| **单一职责（Single Responsibility）** | 每个模块只负责一个明确的业务能力，接口精简且语义清晰 |
| **显式接口契约（Explicit Contracts）** | 模块间交互必须通过显式定义的 Service 接口完成，禁止直接操作其他模块的内部数据或私有函数 |

## 2. 总体架构

### 2.1 架构风格

系统采用 **前后端分离的单体分层架构（Monolithic Layered Architecture）**：
- **后端**：单个 Python Flask 进程，内部按领域模块纵向拆分，按接口层/领域层/基础设施层横向分层；
- **前端**：三个独立的 Vue3 SPA（学生端、管理端、AI 助手），通过 REST API 与后端交互；
- **数据层**：单一 MySQL 实例，各领域模块通过 ORM 访问各自领域的数据表。

## 3. 模块划分

系统后端采用 **三层架构**，自上而下分为：
- **接口层（API Layer）**：3 个独立的接口模块（学生端 / 管理端 / AI 端），负责协议适配；
- **领域层（Domain Layer）**：6 个业务领域模块，负责核心业务规则；
- **基础设施层（Infrastructure Layer）**：5 个独立的基础设施模块，负责技术能力支撑。

### 3.1 业务领域模块总览（Domain Layer）

业务领域模块是系统的核心，每个模块封装完整的业务规则与数据，对外暴露 Service 接口。

| 模块标识 | 模块名称 | 职责概述 | 对应数据实体 |
|---------|---------|---------|-------------|
| `MOD-USER` | 用户与权限模块 | 用户管理、角色管理、权限管理、登录认证、RBAC 校验 | User, Role, Permission |
| `MOD-ROOM` | 自习室与座位模块 | 自习室管理、座位管理、动态签到码生成与校验、座位可用性计算 | StudyRoom, Seat, SignInCode |
| `MOD-RESV` | 预约与签到模块 | 预约提交与取消、时间冲突检测、签到、违约判定与记录、定时任务触发 | Reservation, ViolationRecord |
| `MOD-NOTIF` | 通知模块 | 通知生成、查询、标记已读、未读统计 | Notification |
| `MOD-SYS` | 系统配置模块 | 系统参数的配置与读取，支持运行时热更新 | SystemConfig |
| `MOD-AI` | 智能助手模块 | 意图识别、多轮对话管理、大模型调用、结构化回复生成 | （无独立实体，依赖其他模块） |

### 3.2 接口层模块划分（API Layer）

接口层**不是业务领域模块**，而是各领域模块的 **RESTful 接入适配器**。每个前端入口对应一个独立的接口模块，职责仅限于：参数解析、身份鉴权、调用 Domain Service、序列化响应。

| 模块标识 | 模块名称 | 职责 | 映射的前端 |
|---------|---------|------|-----------|
| `API-STU` | 学生端接口模块 | 学生端全部 REST 路由，调用 USER / ROOM / RESV / NOTIF | 学生端 SPA |
| `API-ADM` | 管理端接口模块 | 管理端全部 REST 路由，调用 USER / ROOM / RESV / NOTIF / SYS | 管理端 SPA |
| `API-AI` | AI 助手接口模块 | AI 端全部 REST 路由，调用 AI（AI 内部再调用其他 Domain） | AI 助手 SPA |

**约束**：接口层模块之间**禁止互相调用**；每个接口模块只能向下调用领域层 Service，不能直接操作数据库或跨接口模块复用逻辑。

### 3.3 基础设施模块划分（Infrastructure Layer）

基础设施层**不是业务领域模块**，而是为上层模块提供通用技术能力的**可替换组件集合**。每个组件职责单一，可被多个领域模块共享。

| 模块标识 | 模块名称 | 职责 | 被哪些模块依赖 |
|---------|---------|------|--------------|
| `INF-DB` | 数据库访问模块 | SQLAlchemy ORM 初始化、连接池管理、迁移辅助 | 全部领域模块 |
| `INF-AUTH` | 认证与加密模块 | JWT 签发/校验、密码哈希、RBAC 辅助工具 | API 层、USER 模块 |
| `INF-CACHE` | 缓存模块 | 进程内缓存 / Redis 封装，提供 get/set/expire 抽象 | SYS、ROOM（可选） |
| `INF-MSG` | 消息网关模块 | 邮件 / 微信 / 短信发送接口的抽象与实现 | NOTIF（可选） |
| `INF-EXC` | 异常与响应模块 | 全局异常基类定义、统一响应格式、HTTP 错误码映射 | API 层、全部领域模块 |

**约束**：基础设施模块**禁止依赖任何业务领域模块**（例如 `INF-AUTH` 不能 `from domain.user import ...`），保持纯粹的技术无关性。

### 3.4 模块与前端入口的映射关系

| 前端应用 | 接口层模块 | 涉及领域模块 |
|---------|-----------|-------------|
| 学生端 SPA | `API-STU` | USER, ROOM, RESV, NOTIF |
| 管理端 SPA | `API-ADM` | USER, ROOM, RESV, NOTIF, SYS |
| AI 助手 SPA | `API-AI` | AI（内部调用 ROOM, RESV, USER） |

## 4. 分层架构详细设计

### 4.1 接口层（API Layer）

接口层由 **3 个独立的接口模块** 组成，是系统的**北向入口**。每个接口模块职责仅限于：
1. **接收 HTTP 请求**，解析 Query / Body / Path 参数；
2. **身份认证与权限校验**（JWT 解析、RBAC 装饰器，由 `INF-AUTH` 提供能力）；
3. **参数基础校验**（必填项、格式、范围）；
4. **调用领域层 Service** 完成业务处理；
5. **序列化响应**，返回统一 JSON 格式（由 `INF-EXC` 提供能力）。

**约束**：
- 接口模块**不包含任何业务逻辑**，禁止直接操作 SQLAlchemy Model；
- 接口模块之间**禁止互相调用**；
- 学生端与管理端如有相似功能（如"查询预约记录"），必须分别调用各自的 Domain Service，禁止在接口层做逻辑复用。

### 4.2 领域层（Domain Layer）

领域层是系统的**核心**，包含全部业务规则与业务逻辑。每个领域模块由以下要素构成：
- **`models.py`**：领域实体（SQLAlchemy Model），仅在模块内部使用，不对外暴露；
- **`service.py`**：领域服务接口，是模块对外暴露的唯一合法入口；
- **`dto.py`**（可选）：数据传输对象，用于模块间传递结构化数据；
- **`scheduler.py`**（可选）：领域相关的定时任务逻辑。

**核心约束**：
- 模块 A 若要使用模块 B 的能力，**只能调用 `B.service` 中定义的函数**，禁止直接 `from B.models import ...`；
- 领域模块之间尽量保持**单向依赖**，避免出现循环依赖。

def call_llm(prompt: str, context: list[dict] = None) -> str:
    """

  - `MOD-RESV`：查询用户预约记录；
  - `MOD-NOTIF`：查询未读通知数（可选）。

**约束**：AI 模块作为**上层消费者**，依赖多个下层领域模块，但自身不暴露给其他业务模块（只被 `API-AI` 调用）。

## 8. 关键技术决策

### 8.1 为何采用单体而非微服务？

- **团队规模**：6 人小组，微服务带来的运维复杂度远超收益；
- **课程周期**：6 周 3 轮 Sprint，需要快速集成与演示；
- **部署成本**：单体应用单进程+单数据库即可运行，降低环境搭建成本；
- **演进预留**：模块间通过显式 Service 接口交互，未来如需拆分为微服务，可将 `domain/xxx/service.py` 整体替换为 RPC 客户端，接口层改动极小。

### 8.2 领域模块间的解耦策略

| 场景 | 策略 |
|------|------|
| 同步查询（如 AI 查座位） | 直接调用目标模块的 Service 接口 |
| 副作用通知（如预约成功发通知） | 优先采用**同步调用** `MOD-NOTIF.send_notification()`，保持简单；如后续通知逻辑变重，可改为异步队列 |
| 跨模块数据一致性（如注销自习室需取消预约） | 由 `MOD-ROOM` 显式调用 `MOD-RESV.cancel_future_reservations_by_room()`，在单体架构中属于可控的紧耦合；未来可演进为领域事件模式 |

### 8.3 缓存策略

- `MOD-SYS.get_config_as_int()`：使用进程内 `functools.lru_cache`，配置更新时手动清除；
- `MOD-ROOM.get_seat_availability()`：可用时段计算结果可缓存 1–5 分钟（Redis 或本地缓存），降低高并发查询压力；
- `MOD-USER.get_user_permissions()`：JWT Token 中已携带权限列表，无需重复查询数据库。
