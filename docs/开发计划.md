# 自习座位预约系统开发计划

## 1. 项目背景与当前状态

本项目为高校自习座位预约系统，分为学生端、管理端和 AI 智能助手三大模块。小组共 6 人，按功能划分为 3 个小组并行开发：

- **系统-管理员部分**（2人）：负责管理端 Web（Vue）及对应后端 API
- **系统-学生部分**（2人）：负责学生端应用（Vue Web）及对应后端 API
- **AI 智能化部分**（2人）：负责智能助手聊天框、NLP 解析及 AI 相关后端服务

**当前状态**：
- 需求文档、数据库设计、API 接口文档已完成
- 后端数据模型（`backend/common/models.py`）和种子数据（`backend/seed.py`）已完成
- 后端业务 API（`admin/routes.py`、`student/routes.py`、`ai/assistant.py`）仅含 TODO 占位，尚未实现
- 三个前端项目已初始化（Vite + Vue3 + Element Plus），但无实际页面代码
- 认证、测试、CI/CD、定时任务均未开始

开发周期采用 **3 轮冲刺（Sprint），每轮 2 周，共 6 周**，目标是在第三轮结束后系统达到可演示、可交付状态。

---

## 2. 冲刺总览

| 冲刺 | 周期 | 主题 | 核心目标 |
|------|------|------|----------|
| 前置基础 | 第 0 周 | 公共基础设施搭建 | 认证体系、统一响应、路由骨架、前端公共库、迁移环境 |
| Sprint 1 | 第 1–2 周 | 基础架构 + MVP 打通 | 完成后端核心 API 和前端基础页面，实现"查座位→预约→查看记录"完整闭环 |
| Sprint 2 | 第 3–4 周 | 完整业务 + 权限 + AI 基础 | 补全签到、通知、违约、RBAC 权限、AI 关键词匹配对话 |
| Sprint 3 | 第 5–6 周 | 智能化增强 + DevOps + 集成测试 | 接入大语言模型、搭建 CI/CD、编写自动化测试、全系统集成优化 |

## 7. 跨组协作与依赖管理

### 7.1 接口契约

所有小组共享 `backend/common/models.py` 和数据库结构。各组在开发 API 时，需遵守 `docs/API接口文档.md` 中的约定。若需变更接口，必须在组内站会中同步，并更新文档。

### 7.2 关键依赖路径

```
Week 0:
  公共组   ──► auth.py + utils.py + 路由骨架 ──► 已✅完成，三组可并行开发

Week 1:
  管理员组 ──► 自习室/座位 CRUD ──► 阻塞学生端预约时的数据展示
  学生组   ──► 座位可用时段计算函数 ──► 阻塞座位查询和预约
  AI组     ──► /ai/chat 接口格式 ──► 阻塞前端聊天组件对接

Week 3:
  学生组   ──► 座位/预约查询内部函数 ──► 阻塞 AI 组接入真实数据
  管理员组 ──► RBAC 装饰器 ──► 阻塞管理端权限控制页面

Week 5:
  全组     ──► 合并到 main 分支 ──► 阻塞集成测试和 CI 配置
```

### 7.3 代码分支策略

- `main`：稳定分支，仅合并已通过自测的功能
- `feature/xxx`：各小组按功能创建分支，命名规范：`feature/sprintN-模块-功能`
- 每周至少合并一次到 `main`，合并前需进行代码审查（至少另一组一人 review）

### 7.4 沟通机制

- **每日站会**：三个小组各派 1 人参加（共 3 人），15 分钟同步进度和阻塞点
- **API 文档维护人**：由管理员组指定 1 人负责维护 `docs/API接口文档.md`
- **Bug 跟踪**：使用 GitHub Issues 记录，按 `bug`、`backend`、`frontend`、`ai` 打标签

## 8. 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| 后端 API 开发延迟，阻塞前端 | 高 | Sprint 1 优先完成后端接口；前端可先基于 Mock 数据并行开发 |
| 定时任务部署复杂（Celery 重） | 中 | 采用 APScheduler 轻量方案，避免引入 Redis 和 Celery |
| AI 大模型 API 调用不稳定/成本高 | 中 | 始终保留关键词匹配作为 fallback，LLM 用于增强体验而非必需 |
| 组员进度不一致，集成困难 | 中 | 每周强制合并到 main 一次，早发现早解决冲突 |
| 数据库查询性能差（座位可用性计算） | 中 | Sprint 3 专门预留数据库索引优化和查询优化时间 |
